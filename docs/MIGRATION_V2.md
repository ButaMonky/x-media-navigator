# TypeScript v2 再設計・検証計画 (2026-10-25)

## 現段階の判定

- `IMPLEMENTED`: `src/` にロジックを実装、`tsc` で `extension/content_script.js` を生成。
- `TESTED-UNIT`: Node.jsのpure/core + モックDOMテストで確認。
- `NOT VERIFIED`: 実際のX Web UI、Chromeに読み込んだ実運用。
- `BLOCKED-LOCAL`: PCローカル操作は安全性チェックで拒否。GitHub側のみ修正し、元のPCファイルは変更しない。

## v1.3 → v2 の違い

| 機能 | v1.3 | v2 開発版 |
| --- | --- | --- |
| 言語 | JavaScript直編集 | TypeScript正本・JS自動生成 |
| 左右キー | X標準処理を強制停止、一覧へ移動 | v2.1以降：写真の端だけ別投稿へ（確実な判定があるとき）、それ以外はX標準 |
| 投稿間移動 | 左右キー・独自矢印 | v2.1以降：写真の端で左右キー・専用ボタン |
| タイル識別 | statusIdのみ | statusId + kind + mediaIndex |
| タイル探索 | ページ全体 | プロフィールメディア一覧のmain領域に限定 |
| DOM要素 | 古いElement参照を保持 | 移動時に現在のDOMから再検索 |
| DOM変化 | 固定ポーリング中心 | MutationObserver（一覧） + 450ms安全側フォールバック |
| 遅延読み込み | scrollから300msで完了と推定 | 新規タイルを最大4秒確認、なければ誤遷移しない |
| UI部品 | div疑似ボタン | button + aria-label + disabled状態 |
| 拡張権限 | host_permissions | host_permissionsなし・content_scriptsのみ |

## 解決した不具合（コードレベル）

- AUD-001: 未修飾の左右キーを横取りしない。
- AUD-002: URLに記載されている画像/動画の番号を別のタイルとして追跡。
- AUD-003: DOMノードを持続キャッシュせず再探索。
- AUD-004: アカウントを切り替えたら採番もゼロから再構築。
- AUD-005: 新規項目検知後だけ遷移。新規項目がなければ既存タイルへの誤移動を防止。
- AUD-006: `/media`で取得した一覧の文脈を保持。`/status`に入った際は関連投稿を収集しない。
- AUD-007: 日本語と英語の閉じるボタンを検出。検出不能なら移動せずに通知。
- AUD-008: 入力中・修飾キー・長押しによる競合の一部を防止。
- AUD-009: 他プロフィールのタイルを除外。

## 既知の制約と残余リスク

1. XがDOMや `data-testid` を変更した場合、ビューア認識に失敗する可能性。
2. メディアタイルへのリンクに `/photo/N` や `/video/N` がなければ、同一投稿の複数メディアを常に区別できるわけではない。
3. 仮想スクロールで画面外のDOMが消えた場合、記録済み項目の再検索・復元が不十分。発見できないときは移動を中止。
4. 次の未ロードの項目がない場合は、ビューアをいったん閉じて最大4秒探索する。その後に原項目へ戻すベストエフォート動作はX実機では未検証。
5. 閉じるUIのラベルが日本語・英語以外の場合、独自遷移が停止する可能性。意図しないリンクは開かない方を優先。
6. `querySelector('main [data-testid="primaryColumn"]')` と `li[role="listitem"]` の形は現行X実機で未検証。
7. ユーザーのPC上の既存拡張はまだv1.3。ローカルへの同期と導入は未実施。

3. 投稿の終端、追加読み込み、動画・GIF、入力フォーム、メディアタブに戻る操作。
4. 長距離スクロールとDOM仮想化、英語・日本語UI、Chromeのズーム率差。
5. 安定が確認できたらPRレビューの上でmainへマージし、開発用拡張の導入を選択する。

## v2.1（2026-10-25）境界ナビゲーションと先読み

- 無修飾の右矢印はXの写真送りを優先し、**確認できた最終画像**でだけ次の**投稿ID**へ移動。
- 無修飾の左矢印はXの写真戻しを優先し、**最初の画像**でだけ前の**投稿ID**へ移動。
- 従来のShift+左右の独自ショートカットは廃止。専用の◀▶ボタンは投稿間移動として維持。
- 同じ投稿に複数の画像タイルがあっても、投稿間移動ではその画像をスキップする。
- 画像数が不確かな場合の右キーはX標準操作を優先。動画の左右キーを奪わない。
- 前後最大2枚の画像をX公式画像CDNから `name=large` で低優先度プリロード。`Save-Data` / 2G / オフライン / 非表示タブでは行わず、画像以外は取得しない。
- Xは元からSPAであり、ここでは画像資源を先読みする。モーダルの閉じる→開き直しは引き続き実行されるため、完全な無瞬断は保証しない。
- **Chromium模擬ページ／TypeScript単体検査**とX実サイトの証拠は区別する。実サイト確認までDraft PRを保つ。

## v2.2 (2026-10-25) 確定度・タイムライン分離の再設計

- 同一プロフィールの `/media` と `/media?filter=photo`・`?filter=video` を別のセッションキーで管理。
- 写真/動画フィルターを変えた直後、URLのみ先に変化しても旧DOMを新しい一覧として採番しない。新DOMに置き換わるまで安全に待機。
- `photoCount` が見えた1〜3枚だけから総枚数を断定する処理を廃止。表示と一致する明示カウンター、またはX公式上限4枚が全て見える場合のみ最終枚数を認定。
- 部分的な写真情報しか見えない場合、右キーの投稿間移動が利用できないことがある。これは誤移動よりもX標準操作を優先する意図した仕様。
- 先読み写真は最大2枚のまま、画像デコードをbest effort実行、サムネイルURL記憶は最大128件。
- URLを450msごとに確認するフォールバックは維持するが、DOMが変わらないときはリスト全件走査を繰り返さない。
- GraphQL内部エンドポイントへの直接通信・認証ヘッダーの抽出は追加せず、既存権限で動作。
- モックDOM・Node型検査・Chromium擬似X・本番Xは異なる検証種別として記録する。

詳細: `docs/research/2026-10-25-media-timeline.md`。実機でXがUIを変更した場合は再評価が必要。

## v2.2.1: SPA・仮想DOMのナビゲーション保全（2026-10-25）

- **既知の移動先が仮想化などでDOMから消えていたら、先にビューアを閉じない。** 同じ投稿を閲覧し続けられるようにし、短い通知を出す。
- ビューアを閉じた直後、写真/動画フィルターを含むタイムラインキーが元の一覧と一致することを確認する。異なる場合は古い一覧からの遷移を中止する。
- 既に見つかっている対象と、新規スクロールでまだ見つかっていない対象は区別する。後者の安全な再読み込み待機処理は維持する。
- TypeScriptを正本とし、Chrome用JSはビルド生成物として更新。Chromium模擬テストには「既知の遷移先DOMが消えた」ケースを追加する。
- タブURLをXが戻り時に書き換える場合は安全側で遷移を中断する可能性があり、本番Xでの検証が必要。

## v2.2.2: 右キー不動作の修正（2026-10-25）

- ユーザーの実機報告：v2.2.1-beta1で→を押しても次のポストへ進まない。対象投稿のDOMスナップショットは取得できていないため原因はソース監査からの推定。
- 1〜3枚の投稿で、同一statusIdの写真タイル群が完全な1..Nのリンク列として存在する場合は、明示カウンターがなくても末尾を確認する。
- 総枚数が依然不明な場合はX標準の画像送りを先に通す。進まなければ「もう一度→で次の投稿へ」と通知し、再操作時に投稿間移動する。X標準の画像送りを確認できた同一投稿では後続の終端を遅延検証して一度のキーで移動可能にする。
- フィルター付きメディア一覧へ戻る際にXがfilterパラメータだけを削除する場合は、**同じ実DOMリンク／タイムラインの維持**を検証してから移動を許可。明示的な別フィルターへの切替は拒否。
- ナビゲーション中の450ms URLポーリングが、閉じた直後の一時的なフィルター省略でセッションを初期化しないように修正。
- ソースコード・Node・Chromium模擬テストと実際のXのユーザー操作は別判定。X本番での修正成功は未確認。
- 詳細は `docs/research/2026-10-25-right-arrow-fix-v222.md`、追跡はIssue #14。

## v2.3.0 experimental（2026-10-26）先読み／SPA視覚引継ぎ

- 同じ投稿の次写真と別投稿の先頭写真を、アルバムの途中から最大2件先読み。decode()成功したものだけ再描画用として準備完了扱いにする。
- 別投稿へ切り替わる間のみ、既にデコード済みの画像をpointer-events:none、aria-hidden=trueの視覚的レイヤーとして最大1.8秒表示。新しいXビューアを認識したら短時間で解放。
- XのSPA・React Router・履歴・内部API・認証へ介入しない。動画は対象外、低速回線・省データ・タブ非表示・モーション低減では適用を制限。
- PCで確認中のv2.2.3には反映しない。新しい研究ブランチに実装し、模擬ブラウザ／Node／CIのテストと実際のXにおける確認を分けて記録する。

## v2.4.0 — 先読み・終端判定・SPA表示の研究実装（2026-10-26）

- 画像の先読み候補を最大5件まで増やしつつ、同時ネットワーク要求は最大2件に制限。3G/省メモリ環境は2件、Save-Data・2G・オフライン・非表示タブでは追加取得しない。
- デコード済み画像の短期キャッシュは最大6レコード、概算80MiBを上限に管理。再訪時の再ダウンロードを減らし、失敗URLの無限再試行も防ぐ。
- 投稿切り替え時の引継ぎ表示は画像エリアを優先して覆い、Xの新しい画像が読み込み済みと確認できるまで解除しない。最大1.8秒の安全タイムアウト付き。
- 完全なSPA切替（右側のツイート欄を閉じずに次投稿を表示）は未実装。現状の閉じ→開き直しに由来するアニメーションは残りうる。
- Xの最新カルーセルで、画面に1〜3枚しか見えていないことを「全部」と決める判定を廃止。ARIA画像カウンター、明示的に無効化されたネイティブ送りボタン、4メディア上限から終端を判断。
- 一度確定した投稿の画像総数はセッション内で最大128件保持。初見の投稿で十分な情報がなければ右キー2回の安全な確認方式を維持する。
- 詳しい根拠と検証状況：[v2.4.0 研究レポート](docs/research/2026-10-26-fast-gallery-v240.md)。GitHub Actions/模擬ChromeテストとX実機での速度改善は区別する。

## v2.4.1 — SPA検出の待機短縮・オーバーレイ安全化（2026-10-26）

- 従来の450msルート確認と350ms先読みdebounceが重なる遅延を緩和。メディア一覧時だけViewer DOM追加・除去のMutationObserverを監視し、生成後の先読みタイマーを0msにした。
- React内部の非公開API・History monkeypatchは行わず、450msの定期確認を安全側フォールバックとして残す。
- 引継ぎ画像の矩形を特定できない場合、右の投稿欄を覆う全画面黒レイヤーを表示しない。
- 超高解像度のデコード画像が単独で80MiBを超える場合に無駄なキャッシュ再取得を防ぐ。
- 検証：Node/FakeDOM、合成Chrome、GitHub Actions、X実サイトを区別して記録。詳細は docs/research/2026-10-26-prefetch-startup-v241.md。
- X本番での画面変化・体感速度、投稿欄アニメーションの根本解決は未確認。mainおよび既存Web Store版は変更しない。
## v2.4.2 — クリック直後先読みと遅延サムネイル補足（2026-10-26）

- DOMのメディアタイルが実際に左クリックされた瞬間から、ネイティブXのルートを邪魔せず先読みを開始。新しいモーダルを待たずに最大2件を低優先度で準備、のち最大5件に拡張。
- Save-Data・3G以下・4GiB以下では初回メディア描画との通信競合を避けるためクリック直後の先読みを行わない。修飾キー・中クリック・引用など無関係リンクでは動かない。
- メディアタブの監視対象に `src/srcset` の属性変更を追加し、遅れて読み込まれるXのサムネイルCDN URLを再取得。無関係な属性変更は除外。
- `docs/research/2026-10-26-preopen-prefetch-v242.md` に根拠・制約・SPA実装の代案を記録。X本番での高速化と右側パネルの再生成抑制は未検証／未実装。

## v2.4.3（2026-10-26）属性変更の部分スキャン

- `MutationObserver`が捕捉した`src/srcset`更新を対象タイルだけで処理し、毎回全メディア一覧を再走査する負荷を軽減。新タイル・メディアリンクの追加/削除では順序整合性を再検証。
- 構造変更・属性更新が100ms以内に重なった場合は1回の全体スキャンに統合する。
- `imageSources`のURLが同一なら再登録しない。新URLならリビジョンを進め、次回の先読み候補更新を確実にする。
- 詳細は docs/research/2026-10-26-targeted-media-source-v243.md。実際のXでのCPU・速度改善率は未測定。
