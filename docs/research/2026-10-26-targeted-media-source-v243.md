# X Media Navigator v2.4.3 — サムネイル更新の部分走査とキャッシュ再利用

2026-10-26 / 開発元：v2.4.2 (e74ecc8)

## 確認した問題（SOURCE VERIFIED）

v2.4.2の `ensureListObserver` は `img.src` / `img.srcset` の属性変更を検知できる。しかし、1つのサムネイルだけのURLが更新されても、100ms後に `scanTiles()` を実行していた。

`scanTiles()` はメディア一覧の全 `li[role=listitem]` を走査する。長い一覧で画像がK件順に更新されると、各イベントでN件の走査が起こり得るため、CPU負担とDOM操作を余計に増やす可能性がある。

さらに、従来は取得済みの同一サムネイルURLも `Map.delete` → `Map.set` で繰り返し登録し直し、LRUの順序を崩していた。これは静的コード分析による事実であり、X本番のCPU実測値ではない。

## v2.4.3実装（CODE IMPLEMENTED）

1. **画像属性の更新は当該タイルだけ**：`src/srcset` 変更を観測したら、変更元の `li` のみに対し、既知の所有者リンクとCDN URLを再確認する。存在しない・不明なリンクは追加登録しない。
2. **DOM構造の変更は引き続き全体整合**：新しいメディアタイル・画像・メディアリンクの追加/削除時だけ、従来の `scanTiles()` で順序・番号・所有者を確認。バッジ自身の更新や無関係なサイドバーのDOM変更では再走査しない。
3. **100msの変更統合**：同じ100ms以内に属性変更と構造変更が混在したときは、1回の構造整合スキャンに統合。先行する属性変更イベントを破棄してしまう競合を防ぐ。
4. **同一URLを再登録しない**：`imageSources`に同じURLが既に登録されていたら何もせず、異なるURLの場合だけ書換。128件の保持上限は従来どおり。
5. **先読み候補の更新を識別**：URLが変わった場合は `imageSourcesRevision` を増加させる。枚数やURLパスが変わらない状態でも、次回の `schedulePreload()` が新しい候補を評価できるようにする。

## 再発防止検証

- Node / Mock DOM：無関係なアバターのsrc変更では再走査しない、対象タイルのsrcだけ変更すると部分更新を1回実行、タイル追加と属性変更が同時発生したら1回の全体スキャンへ昇格することを検証。
- Node / Mock DOM：同じURLはキャッシュ改変/リビジョン増加なし、別CDN画像への変更ではURLを正規化してソースリビジョンが増加することを検証。
- Chrome合成X：画像ナビゲーション、最終画像、先読み、動画のキー操作、SPA引継ぎ、プロフィール範囲、キャッシュ制約を回帰検証。
- X本番では **未測定**。CPU使用率、Image.decode()前後の表示空白時間、pbs.twimg.com転送量はDevToolsで実測する必要がある。

## 研究上の注意

- Xの元のSPAを閉じずに別投稿へ切り替えることはまだ実装していない。右側の投稿欄の再展開アニメーションは依然残る可能性がある。
- 右キー最終画像の判定は明示カウンター・ARIA・ネイティブ画像送りボタン・4メディア上限が根拠。推測で画像を飛ばさないため、不明なら確認操作が残る。
- 先読み最大5画像/同時通信最大2件、低速・省メモリ制限、概算80MiBのデコード済みキャッシュ上限、クリック前先読みの最大2件などは維持する。
- 外部API、GitHub常時同期タスク、ユーザー認証/ページ秘密情報の取得、Xの内部React Router操作は導入していない。
