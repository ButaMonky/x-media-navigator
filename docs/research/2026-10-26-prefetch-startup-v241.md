# X Media Navigator v2.4.1 — 高速化・SPAモーダル監査

2026-10-26 / research branch: fix/prefetch-startup-v241

## 静的解析で判明した遅延（SOURCE VERIFIED）

- v2.4.0では、プロフィールのメディア欄から画像を開いた後、Controller.tick() が 450ms 間隔でルートとビューアを確認する構造だった。
- ビューア検出後の schedulePreload() も 350ms の遅延を設けていた。このため、画像が画面に出てから先読み要求を始めるまで理論上最大約800msの待機があり得た。これは実測値ではない。
- history.pushState/replaceState は popstate イベントを発行しない。ユーザーのリンククリックでXがDOMを組み替えても、単なるpopstate待ちは効果がない。
  根拠：https://developer.mozilla.org/ja/docs/Web/API/Window/popstate_event
- DOMのchildList/subtreeをMutationObserverで監視すればビューア要素の追加・削除を検出できる。
  根拠：https://developer.mozilla.org/en-US/docs/Web/API/MutationObserver/observe

## v2.4.1の修正（CODE IMPLEMENTED）

1. **SPAビューア即時検知：** プロフィールのメディア一覧に入ったときだけ、body配下に現れるビューア要素の追加/除去をDOMのMutationObserverで捕捉。画像ビューアが現れたらそのタイミングでtick()を実行する。XのHistoryやReact内部の関数はフック・上書きしない。450msのタイマーは予備として残す。
2. **先読みの待機を短縮：** ビューアが検出された後の350msのdebounceを、同じタスクキュー上の0msへ変更。すでに保存したタイムライン・パス・先読み候補のキーで重複要求を避ける。X本番での描画/通信ミリ秒改善率はまだ未測定。
3. **右側の投稿欄を覆わない：** 視覚引継ぎレイヤーはXの画像表示領域の有効な矩形を取得したときのみ表示。右側の会話パネルとの境界を確認できない場合、全画面黒背景で覆うことをやめ、X自身の表示に戻す。
4. **巨大画像のキャッシュ・ループ防止：** デコード後の概算メモリが単体で80MiBを超える画像はキャッシュとして保持しない。同じ閲覧セッション中に再スキャンするたびに同画像を再ダウンロードしないよう、対象URLを短い集合へ保存する。6レコード・合計概算80MiB、同時2要求、将来最大5枚の既存制限も維持。
5. **追試：** 同じURLの再取得、巨大画像、モーダルの出現と除去、非表示タブ、未知のビューア矩形の回避に対する検査を追加。

## 画面遷移の方式と限界

**今回もX本来の画像ビューアを閉じて別の投稿を開く方式は変更していない。** 右の投稿・返信欄の開くアニメーションを根本的に除去したわけではない。ChromeがXのモーダルを再生成する際に視覚引継ぎが間に合う確率を上げ、右欄が黒く隠れる事故を減らすための調整である。

v2.4.0で報告された「成功/失敗がおよそ半々」というのはユーザーの体感報告。確率として未測定のため、v2.4.1が常に成功する・xx%高速化する、と断定しない。

## 検証と資料

- Node/FakeDOMで、タイマー遅延を0msとすること、SPA追加/除去をobserverが即検知すること、無関係なDOM変化で再スキャンしないことを検査。
- Chromeの合成Xでは、ギャラリーの読み込み後350ms未満に最初の先読みが始まる条件と、右側欄を覆わない写真の引継ぎ領域を検査。
- npm test と npm run typecheck、実Chrome合成Xのテスト、GitHub Actions の push/PR 検査結果を別々に記録。
- **X実サイトのDOM、写真/動画の挙動、描画空白時間、実CDN転送量、右欄アニメーションは未検証。**
