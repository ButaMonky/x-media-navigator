# X Media Navigator — FxEmbed一括APIと従来Xメディア一覧方式の比較評価

- 作業ID: `XMN-API-VS-NATIVE-EVAL-20261031`
- 調査日: 2026-10-31 JST
- 対象: 非公開v2.4.26。公開mainと既存Chrome用Currentは変更しない。
- 根拠: `src/core.ts`, `src/content.ts`, `src/session.ts`, `docs/research/2026-10-28-native-timeline-boundary-api-v2418.md`、公開FxEmbed/X/Chrome公式文書、匿名化した一時HTTP試験。本人のCookie、token、HAR、生の投稿ID/URL、画像は保存しない。
- この報告は現行実装の比較・評価であり、製品コードの変更、正式リリースの許可ではない。

## 結論

**通常閲覧の主軸は「Xが実際に表示して読み込んだメディアDOM／X自身のネイティブリンク」にする。** 先読みはX CDNの既知画像について既存の少数・低並列キャッシュを使う。未知の次投稿では背景の強制自動スクロールを復活させず、元のビューア・返信欄・位置を保ち、利用者がXのメディア一覧で追加ロードできるようにする。

FxEmbedは魅力的な「未ロードの投稿を先に見つける」手段だが、**第三者APIのメディア種別、並び順、XのReactビューア復元と一致する保証がないため、標準の必須経路にはしない**。研究・上級者向けの明示的オプションとして維持する余地はあるが、今回はオプトイン既定無効が適切という評価。自動背景取得・再試行は最小化。X公式の課金APIへの自動切替や非公開GraphQL・Cookie利用はしない。

## 実装レビュー（v2.4.26）

- `src/content.ts`: 既知メディアはXの実DOMリンクを優先。未知の一覧終端で`loadPublicMediaContinuation()`を起動。外部承認はプロフィール・タブ単位で確認し、API取得失敗時は「Xのメディア一覧で読み込んでください」と案内。
- FxEmbed URL: `GET https://api.fxtwitter.com/2/profile/{handle}/media?count=100&cursor=...`。1回の継続で最大4ページ、次の8投稿を目標に、リクエスト間300ms、1リクエスト9.5秒timeout、応答上限4,000,000バイト、429/5xx・不正JSON等のクールダウン。認証情報は渡さず `credentials:'omit'`, `referrerPolicy:'no-referrer'`, `cache:'no-store'`。
- 順序検査: 投稿IDの降順、重複投稿群、DOM側の末尾アンカーと直前投稿、同一カーソル・期限・所有プロフィール・フィルターの条件を検証。安全に一致しなければ拒否する。
- `src/core.ts` `parsePublicMediaPage` は「同一投稿の写真のみ1〜4枚」または「動画/GIF1本」の形式だけを採用。**1件でも混合／複数動画など対象外があるとページ全部をnull返却**する（skipしてcursorを進めると投稿喪失となるため、安全側の動作）。
- 最大450メディア参照の不変ページ保存、保存可能なcheckpoint最大64ページ、`chrome.storage.session`とページmanifest等は安全性のため複雑。API-only投稿へ `window.location.assign()` する場合、同一Reactモーダル／元の返信欄を維持する真のSPAではない。
- 既存の画像先読み：既知写真最大5枚・同時2件・デコード済み画像概算80MiB上限、省データ／オフライン停止。**この画像先読みは第三者API一括取得とは別機能なので維持可能**。

## 限定的な実通信検証（公開プロフィール、集計のみ、個人データ未記録）

- 通信元: 認可されたWindows PCから、明示的な識別用User-Agent、`Origin: https://x.com`、JSON Accept。Cookie・token・Referrerなし。実Xのログイン済みブラウザ／UIは使用していない。
- API `count=1`: 一度HTTP 500（独立のクライアントではUser-Agent未指定で401。これは**識別用User-Agent必須**というサーバーの案内であり、ブラウザで401になった証拠ではない）。要求サイズによる違い、時間変化、上流の状態は確定していない。
- API `count=100`: 独立試行でHTTP 200、返された投稿数はおおむね**61〜73件**、`cursor.bottom`あり。1回の応答は約1.2秒の例があった。常に速い／正確との保証ではない。
- API `count=100` の取得JSONを、変更していないv2.4.26実物の`parsePublicMediaPage`で評価：**false/null**。ある標本では73投稿のうち、写真のみ35、動画1本35、対象外3（混合など）。別標本では61投稿中、対象外2（型の構成は`video+photo+photo+photo` 1、`video+photo` 1）。**対象外をテスト上除外した場合だけ解析PASS**し、92個の画像/動画参照を作れた。これは原因分析用の操作であり、実装として除外してcursorを進めることは厳禁。
- API `count=20`: HTTP 200、10投稿、メディア構成は写真のみ8＋動画1本2、解析PASS、次cursorあり。約4.1秒・受信約44KB。小分けは不合格を局所化する可能性はあるが、混合投稿を通過できず、追加のリクエスト・遅延を招く。高速化との断定不可。
- ユーザー提供スクリーンショットではFxEmbedの承認ダイアログ後、投稿一覧終端の次を確認できなかった旨のトーストが表示。これは今回特定した「HTTP成功でもスキーマ不一致で全ページ拒否」という経路と整合する。ただし**当該1回の正確な失敗理由は診断イベント未取得のため確定しない**。
- 既往のユーザー5項目PASS（通常の左右キー／28→29／見た目／返信欄／戻る・動画）は有効。**その成功はFxEmbedの任意の次ページ取得が常に成功するという意味ではない。**

## 正確性と設計のトレードオフ

1. 「mixedをskipして続ける」は推奨しない。投稿抜け・前後順位の破壊や架空`/photo/N`・`/video/N`への移動リスクがある。
2. APIで既知の正確なprefixだけ採用し、不明投稿で停止する方式も検討可能。ただしXがその投稿へ表示遷移できることを保証せず、cursorを誤って進めてはならない。実装は追加検証が必要。
3. API `count=20`で分割すると大きな100件ページの失敗範囲を小さくできる場合があるが、混合を最終的に回避できない。標準移動のために外部照会を自動連打しない。
4. Xのスクロールは画面に既知の画像を追加できるが、旧v2.4.17の裏側で20回探索・最大4秒ほど自動スクロールする方式は元画面を動かす既知問題だった。v2.4.18で明示的に撤去したままにする。
5. X公式User Posts `GET /2/users/{id}/tweets` は最大100件/回、OAuth/開発者枠、課金や制限があり、Web Mediaタブと同じ表示順・同じメディア構成は保証されない。2026年10月時点の公式料金表はPosts Read **$0.005/取得リソース**（100件で約$0.50、実請求は利用量・条件次第）。一般ユーザー向けのChrome拡張に認証トークンを内蔵しない。
6. Xの自動化ポリシー・利用規約は非APIの自動的なサイト操作や無許可スクレイピングを制限する。旧方式の自動スクロール復活や非公開GraphQLの無断利用は、規約と保守性の点でも採用しない。

## 推奨改修案（まだ未実装）

- **P0**: XネイティブDOM・読み込み済み投稿を通常の唯一の真実源にする。画像先読み、ネイティブSPA・返信欄維持は独立して残す。
- **P0**: 外部APIの自動提案・常時バックグラウンドwarmupを標準動作から外し、外部サービスを使わずXのメディア一覧で続きを読み込める導線を明確にする。通知が煩雑なら1回だけ簡潔に案内。
- **P1**: FxEmbedは高度なオプションとして既定OFFにし、操作ごとまたは明確な同意範囲で「外部APIで次を探す」を提供可能。成功・不一致・レート制限・通信不可・混合媒体で明確に停止し、ブラウザ既存位置を変更しない。
- **P1**: 実Xで写真1〜4枚、混合、GIF、末尾・戻る、仮想化によるDOM変更を確認。完了済み通常操作は繰り返し測定しない。
- **P2**: 将来のAPI継続は、X Mediaタブとの順序一致と混合投稿URLの実証後に限り研究再開。単なるHTTP200や「解析で無理やりskip」は受入条件にしない。
- **保護**: 既存Chrome用 `Downloads/X-Media-Navigator-Current`、単一開発worktree、公開main、Draft PR #17はユーザーの方針変更までそのまま。新しいQA版フォルダをPCに増やさない。
