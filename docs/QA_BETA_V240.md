# X Media Navigator v2.4.1：実機速度・誤遷移の検証表

**状態：LIVE X NOT RUN。** GitHub Actionsの自動テストが成功しても、実際のXでの描画・操作速度を保証しない。

## 環境
- テスト専用Chromeプロフィール。旧ベータ版やウェブストア版は同時有効化しない。
- 固定フォルダ：`%USERPROFILE%\Downloads\X-Media-Navigator-Current`。
- 検査対象：GitHubでビルドしたv2.4.0と、必要に応じてバックアップしたv2.3.0。
- Chromeの `chrome://extensions` でバージョンを確認して「再読み込み」、Xのタブもリロード。
- 画像やポストは公開内容を利用し、Cookie、トークン、個人情報、非公開投稿をGitHubへ載せない。

## ギャラリー・キー操作
- [ ] LIVE-01 画像1枚の投稿：右矢印1回で次ポストへ。元画像が1枚かどうかを確定できない場合は誤スキップせず安全側に停止。
- [ ] LIVE-02 画像2枚：1→2はX標準、2→次ポストは右キー1回（総枚数の証拠があるとき）。
- [ ] LIVE-03 画像3枚：1→2→3を飛ばさず、末尾のみ別ポスト。
- [ ] LIVE-04 画像4枚：4枚目は最大4件ルールにより右キー1回で次ポストへ。
- [ ] LIVE-05 同じ投稿を一度離れて再訪した際、確定済み画像総数のキャッシュが使われる。
- [ ] LIVE-06 カルーセルで1枚しか表示されていない4枚画像投稿を、1枚投稿と誤認しない。
- [ ] LIVE-07 動画/GIF、入力欄、修飾キー、写真↔動画タブの切替ではX標準操作を横取りしない。

## 先読み・CPU・ネットワーク
- [ ] SPEED-01 次に既知の投稿が4件以上あるとき、先読み対象が最大5件、同時取得2件以下であること。
- [ ] SPEED-02 Save-Data/2G相当/オフライン/非表示タブでは新規先読みを発生させない。
- [ ] SPEED-03 同じ写真を戻る→進む時に重複要求が増えない。
- [ ] SPEED-04 DevTools Network でX本来の表示URLと先読みURL（name=large等）の完全一致/不一致を記録。
- [ ] SPEED-05 画像1枚・2枚・3枚・4枚、投稿切替でv2.3.0とv2.4.0の中間空白時間・転送量・メモリ使用量を比較。処理の改善を断定する前に繰り返し計測。

## SPAの表示
- [ ] SPA-01 次画像がデコード完了していれば、モーダル切替中に画像が残り、Xの新画像が表示可能になったら解除。
- [ ] SPA-02 左側画像エリアのみを覆い、右の投稿欄に黒い画面を被せない。
- [ ] SPA-03 右の投稿欄が閉じて開くアニメーションの有無、頻度、時間を記録（未修正の場合はIssueへ）。
- [ ] SPA-04 新しい画像が読めない場合でも1.8秒以内にオーバーレイが消え、X標準操作を妨げない。
- [ ] SPA-05 Esc、戻る、ブラウザのナビゲーション、タブ切替、画面ズーム時に残留オーバーレイがない。

**DevToolsの測定**：Networkタブで Preserve log ON / Disable cache OFF。画像URL・転送サイズ・キャッシュ表示と表示切替の時間を記録する。Resource Timing APIの転送サイズはクロスオリジン制限があるため、0Bのみでキャッシュヒットと断定しない。

## 不合格時
- 元のv2.3.0バックアップに戻すか、ベータを無効化する。
- 可能なら公開ポストのURL、画像枚数、期待/実際の操作、Chrome版、Xの表示言語だけをGitHub Issueへ記録。
- GitHubの安定版main、旧ストア版、ユーザーのChromeプロフィールは変更しない。

- [ ] START-01 メディアタブから最初の写真を開いた直後、DevTools Networkに先読み対象の画像リクエストが現れるか。v2.4.0との開始タイミングを比較。
- [ ] START-02 X標準のモーダルを閉じる／再表示する操作で追加の誤移動、二重ビューア、余計なスクロールが起きないか。

- [ ] MEM-01 非常に大きな画像や連続で失敗する画像URLについて、再訪のたびに連続リクエストが発生しないか。

既存の最大5画像／同時2通信と画像総枚数の安全判定は維持する。Chromeの合成ページテストが通ってもX本番での改善率は未測定。
